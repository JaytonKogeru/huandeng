# v0.7 功能与信息架构研究审计

## 1. 范围、基线与方法

本轮先学习创作工具的官方资料，再核对 HUANDENG 的实际调用链、界面和已有交付证据。研究仅生成本报告，没有修改产品源码，没有操作科研原稿、Windows 客户端或 Agent 配置。

审计基于本地 v0.6 源码快照、`WEBCHAT.md` 记录的 Windows 权威 HEAD `20e9e531a04933b3285bf707e2ff57a57085ecdc`、已安装运行时 `9c27465aa88b5b2b59288f5b321596ad10fcb92c`。本地已有 diff 属于交付基线，没有重置。阅读范围包括 `AGENTS.md`、`WEBCHAT.md`、`RELEASE-V06.md`、`PROJECTS.md`、`ANIMATION.md`、历史覆盖审计及相关实现。实际查看了已有截图 [素材库](../evidence/ui-v06/asset-library.png) 和 [动画时间轴](../evidence/ui-v06/animation-timeline.png)。这些是已交付版本的视觉证据，本报告没有把静态阅读冒充为本轮重新执行的 Windows 验证。

本轮职责是任务组织、命令含义、数据归属和可发现性。具体视觉 tokens、微动效和前后端性能由相应审计另行提供，负责人合并时应消除重复。以下优先级是建议；涉及数据模型或新导出后端的事项须纳入总 Spec 后才能实施。

## 2. 先导学习：可以借鉴什么

| 官方来源 | 观察到的设计 | 对 HUANDENG 的适用判断 |
| --- | --- | --- |
| [Penpot：界面](https://help.penpot.app/user-guide/first-steps/the-interface/) 与 [Assets](https://help.penpot.app/user-guide/design-systems/assets/) | 工具栏有图像创建动作，Assets 提供可复用组件、颜色和文字样式；资源库具有导入、查找和拖入画布的任务。 | “素材库”和“放置图片”不是天然相同的任务。问题应从操作目的、路径和结果是否清楚判断，不能只按名词相似删除一个入口。 |
| [tldraw：Actions](https://tldraw.dev/sdk-features/actions) | 菜单、按钮和快捷键可以调用同一个动作定义，动作包含身份、标签、快捷键和处理函数。 | 应首先统一动作及禁用条件，再决定哪些位置值得保留快捷入口。一个任务可以有多个入口，但不能产生不同的隐含结果。 |
| [tldraw：Assets](https://tldraw.dev/docs/assets) | 资源记录与使用它的画布对象分开；上传与解析也分开，粘贴/拖入可进入相应外部内容处理流程。 | 文件入库、创建图片对象、复用已有资源是三个相关动作。它们需要共享资源身份，并在 UI 中说明本次动作是否同时修改当前页。 |
| [Blender：Asset Browser](https://docs.blender.org/manual/en/5.0/editors/asset_browser.html) | Link、Append 和 Append (Reuse Data) 明确表达共享来源、独立副本及依赖复用的差别。 | Main 页面复用和演讲变体应清楚说明“哪些内容继续共享”。不应把复制、固定版本和仅修改一次出现的备注混成一个功能。 |
| [Kdenlive：Rendering](https://docs.kdenlive.org/en/exporting/render.html) | 渲染把输出位置、范围、格式设置、时长和作业结果放入同一个任务；高级选项另行展开，任务基于提交时的内容。 | HUANDENG 的动态交付宜成为一个有范围、时序和结果反馈的导出任务。不能仅增加一个“视频”按钮，让用户自行猜测当前 Presentation、暂停点和基础画面的关系。 |

以上是从官方资料提炼的原则，不是要求照搬完整产品。特别是：Penpot 的 Assets 数据模型不同于 HUANDENG；tldraw 的动作结构不要求本轮引入其依赖；Blender 的数据块机制不适合作为幻灯片格式；Kdenlive 的完整剪辑能力也不是下一版的最低范围。

## 3. 对当前产品的判断

v0.6 已具有可用的项目骨架：一份 Main、多份 Presentation、稳定页面身份、独立 occurrence、章节展开、固定版本、演讲专用备注、资源复用、动画轨道以及按区域处理的基础键盘行为。用户提出的这些方向不应再以“尚未开始”描述。现在最突出的功能设计债务是：同一任务的入口、作用范围和状态没有形成一致的表达，进阶功能还需要用户理解较多内部术语。

关于上下左右与 Tab，`pptd-keyboard.ts` 已区分画布、缩略图、图层、输入控件、对话框、时间轴等作用域；画布对象循环、对象微移、F6 面板切换和原生输入保留有实际实现，F1 也有帮助。下一步应补齐具体复杂情境及可发现性，不应另起一套全局抢键逻辑。时间轴的两种方向键行为目前没有纳入统一帮助，见 W4。

## 4. 具体发现、取舍和验收条件

### W1：素材库的“导入”实际上也在当前页放置图片

**证据。** [`huandeng.tsx`](../../packages/core/src/app/routes/huandeng.tsx) 的 `importImages` 调用 `backend.importImage` 后，直接创建图片对象并执行 `element.add`。同一函数同时传给 [`asset-library.tsx`](../../packages/core/src/app/components/pptd/asset-library.tsx) 的 `onImport` 和“添加原始图片”对话框。前者按钮只叫“导入”，实际并非仅入库。后者除设备文件选择外，还让用户手输 `media/figure.png` 来复用已有资源，但素材库已经具有搜索、预览和“复用到当前页”。截图中顶部“图片”、侧栏“素材”和库内“导入”同时存在，关系没有被说明。

**影响。** 用户不能可靠预测“导入”会不会改当前页；已有素材又有两种完全不同的寻找方式。资源库还因为本次操作要放置对象而依赖一个可编辑页面，容易与“管理项目素材”的预期冲突。这个问题是实际调用和产品表达不一致，并不是已发现重复存储图片字节。

**方案取舍。** 按侧栏可见、尚未打开素材页计算，现状“图片 → 文件选择”是两次 UI 命令，“素材 → 导入”也是两次，之后均进入系统文件选择器。只删除顶部图片入口不会自然降低步骤；侧栏折叠时还会增加路径。建议把素材作为唯一可浏览资源的工作区，并让设备导入、粘贴、拖放共享一个“导入并放置”动作。顶部入口可命名为“素材”或以插入菜单调用该工作区，保留直接导入的高效动作；具体位置与 UI 总审计协调。普通用户流程删除手输文件路径，确有诊断需求时放入高级区域。

如果本轮不提供“只入库”，就明确写“导入并放置”，不要用暗示两种行为的名称。如果决定提供“仅添加到素材库”，它必须是独立、明确的选择，不能改变粘贴和拖入当前画布的自然行为。无需为减少一个按钮增加整层复杂模式。

**验收条件。**

1. 从素材浏览、直接导入、画布拖放和粘贴分别添加同一图片时，结果可预测，错误及只读提示一致；同一次操作不会创建两个对象。
2. 复用已有素材通过预览/搜索完成，不要求记忆路径，也不生成无意义的资源副本。
3. 操作标签能区分只入库与入库并放置；若只实现后者，界面明确说明目标为当前页。
4. 从侧栏折叠、当前页面为空、Presentation 固定版本只读三种状态出发，仍能理解可做的动作和禁用原因。

### W2：顶栏的拥挤来自信息层级，而不仅是间距

**证据。** `huandeng.tsx` 的 `hd-titlebar` 高度为 `h-14`，项目标题、当前演讲集合选择器及 `data-hd-save-status` 被置于同一竖排区域；普通“文档服务已连接”也常驻。中央工具栏另外显示当前页面短码、位置与路径。已有素材库与时间轴截图都展示了这三行。

**影响。** 文档身份、当前工作范围和正常后台状态占据相近视觉权重；字号缩至 10px 并没有减少用户必须判断的信息。即使将三行机械压成两行，任务含义仍不够清楚。

**建议。** 顶栏保留项目身份、当前 Main/Presentation 范围以及主要文件动作，按稳定的水平关系组织。当前页位置由页面导航附近负责，路径进入文件信息或提示。正常连接状态可以移入状态区；恢复失败、冲突、保存错误仍应可见且能直接处理。不要为了清爽隐藏保存失败，也不要把本地文档服务连接称为 Agent 已连接。

**取舍。** 标题过长应截断并可查看完整名称，不能侵占导出和演示操作。集合切换是高频任务，应保持直接可见；连接详情则不值得与每次编辑都相关的导航同等占位。具体尺寸和视觉样式交由 UI 审计，不在此另造一套规范。

**验收条件。** 在常用桌面尺寸、较窄窗口和长中文项目名下，标题、当前集合、保存异常、导出、演示均可辨认和操作；不再将三行文字压进 56px。无异常时不重复展示连接状态；发生错误或恢复待处理时，用户能从可见状态直接到达处理入口。键盘焦点顺序与视觉顺序一致。

### W3：用户需要知道“保存”究竟保存了什么

**证据。** 顶栏“保存”执行 `client.flushAll()`，处理页面文档草稿。项目编排使用 `project.replace` 的显式“保存项目”，Story、图表及动画也存在各自草稿/提交状态。路由正确计算 `auxiliaryDirty`，未完成时会显示未保存提示，并阻止依赖这些状态的放映/导出。因此本轮没有证据证明它谎报“全部已保存”或导致数据丢失；问题是一个未注明范围的全局“保存”无法解决用户看见的全部未保存状态。

另一个容易误删的重复是集合选择器：[`project-panel.tsx`](../../packages/core/src/app/components/pptd/project-panel.tsx) 的 `editingId` 可指向尚未保存的新 Presentation，而顶栏只列出已保存的 Presentation。两个控件当前承担不同状态，不能只因看起来重复就删除其中一个。项目总览具有 `onEditProject` 可选入口，但路由没有提供，空态仍引导用户前往编排区。

**建议。** 本轮先让全局保存与草稿清单对齐：状态提供具体待处理项和直达入口；全局保存若不能提交所有类型，就标明页面保存范围，或在有其他草稿时进入统一处理面板。不要以循环发送几个写操作冒充原子“全部保存”。项目总览到编排区域增加明确动作，编辑中的未保存 Presentation 要始终可找回。

**取舍。** 将所有编辑都改成自动保存会牵涉验证、撤销边界及外部 Agent 冲突，并非纯 UI 优化。第一阶段保留独立草稿的保护机制，优先消除用户按下保存却仍不知道下一步做什么的状态。若后续设计全保存事务，要在总 Spec 定义失败时哪些已提交、哪些仍保留。

**验收条件。** 分别制造项目、Story、图表、动画的待处理草稿，点击主保存动作后均能得到准确结果或明确下一步；任一失败不得把其余未保存状态抹掉。新建但尚未保存的 Presentation 可以被定位、继续编辑、保存或放弃。切换 Main/Presentation、关闭面板和遇到外部修改时保留现有草稿保护。F1 对 Ctrl+S 的说明必须与实际范围一致。

### W4：动画底座已存在，首个可见结果仍需要指导

**证据。** [`timeline-panel.tsx`](../../packages/core/src/app/components/pptd/timeline-panel.tsx) 的 `addTrack` 自动创建 0 和末尾两个关键帧，两者取同一个基础值，然后选中起点并将播放头归零。用户直接播放会得到不动的画面。顶部时长与播放读数以秒表达，关键帧字段和步骤字段却要求毫秒。左右方向键在时间轴普通区域移动播放头，在关键帧按钮上则修改关键帧时间；这两种作用分别有实现，但 [`pptd-keyboard.ts`](../../packages/core/src/app/lib/pptd-keyboard.ts) 的统一 F1 帮助尚未包含时间轴章节。

**建议。** 创建首条轨道后给出具体下一步，例如选中终点并聚焦“终点数值”，标明当前编辑的是哪一时刻；保持起始值来自原始对象，避免自动编造移动距离。可见的时间输入统一为秒，允许 0.001 秒精度，底层 `timeMs` 无需迁移。若改用时间码或帧，应统一整个工作区，不要再添第三套默认单位。焦点样式和帮助须明确“移动播放头”与“移动关键帧”。

**取舍。** 自动录制画布姿态和复杂运动路径很有价值，但会引入基础值与预览姿态的写入规则。它们应在下一阶段明确模式后做，不能用隐含自动打帧取代本轮的可理解性改善。现有预览模式不能普通编辑、草稿冲突保护和手势提交边界应保留。

**验收条件。** 首次使用者从选中对象出发，只依靠界面提示完成“从原位移动到新位置并预览”；创建轨道后不会误以为程序坏了。输入 1.25 秒后，保存重开仍为 1250ms；无效输入有反馈，不默默改成另一时间。关键帧焦点与轨道焦点下的方向键、Shift 加速、Home/End、Space 均有可发现说明；文本输入中的原生按键不被吞掉。

### W5：动态导出需要被设计为一次完整的交付任务

**证据。** `huandeng.tsx` 的 `exportDeck` 只接受 `pptx | pdf`，通过当前 `selectedPresentationId` 请求后端，再下载文件；顶栏格式按钮不要求用户确认范围。“导出说明”在完成之后才出现。动画文档和时间轴提醒已说明现有静态格式输出基础画面；动画并未在 PPTX/PDF 中变为可播放对象。这是明确缺口，而不是现有静态导出的缺陷被隐藏。

**建议。** 统一“导出”入口，在提交任务前展示输出范围、格式和可预期效果。至少区分当前页、当前已保存的 Presentation、Main 全部页面中本阶段真正支持的范围；静态基础画面与动画视频必须显式命名。若新增当前播放头静帧，明确其时间。视频需要可理解的分辨率、帧率、时长和保存位置，显示进度、取消、成功结果和失败原因。保留高级参数折叠，普通使用者无需先理解编码器。

对于演讲编排，播放时等待讲者点击的 cue 不是一个有限的视频停留时长。导出 Spec 必须给出规则：例如单页仅输出自身时间轴，或者为演讲各页/停顿明确配置持续时间。不能不声明就无限等待，也不能随意替用户决定讲稿节奏。多页范围要按实际 occurrence 顺序解析，包含重复出现、固定版本和独立备注的正确归属；不要按唯一 pageId 去重输出。

**取舍。** 最小可交付范围可以先做“当前页动画视频”，前提是 UI 明确这一限制且能产生可播放文件。多页视频、旁白和音轨可以另设里程碑。具体编码方案、格式支持及资源约束由负责人结合后端审计决定。本建议不把单纯写出若干 PNG 等同于完成视频导出。

**验收条件。** 在点击开始前就能知道哪些内容将输出、哪些保持静态；执行过程中编辑状态和导出快照的关系清楚。完成后得到外部播放器可播放的文件，长度、首末帧及至少一个中间动画状态符合配置；取消或失败不遗留一个被当作成功结果的损坏文件。静态 PPTX/PDF 功能继续可用。Presentation 有未保存草稿、缺失引用或固定版本问题时，能直达修复位置。

### W6：同一页重复引用是正确模型，变体是另一种需求

**证据。** [`PROJECTS.md`](../PROJECTS.md)、项目模型和 [`project-overview.tsx`](../../packages/core/src/app/components/pptd/project-overview.tsx) 已区分稳定 `pageId`、Presentation item 和解析后的 occurrence；总览能列出当前页在各场演讲中的出现位置。项目面板允许章节展开为独立单页引用、固定命名版本和设置一次出现的独立备注。重复目录页不需要复制内容才能在第 3、16、32 页出现。现有独立备注不等同于独立视觉覆盖层。

**产品判断。** 用户所举的 S18A 在多个位置出现时，保留同一个页面身份、分配各自 occurrence 是合理的默认行为，位置本身不应变成内容身份。如果每次目录页需要高亮不同章节，视觉内容确实不同，就要显式创建变体或另有经过设计的状态模型。不能悄悄改共享 Main，导致其他出现一并变化。

**建议。** 先把“这次出现引用什么、哪些演讲会受影响”放在可见上下文中，并提供从总览到编排的直接定位。长演讲需要按标题、短码查找页面/条目，减少几十项列表中的逐行上下移动。后续“为这次出现创建独立变体”应将复制页面、产生新身份、保留资源引用、替换指定 occurrence 的引用作为一个清晰操作；若现有事务无法保证整体结果，不应在 UI 中伪装成一步已完成。

**取舍。** 立即加入任意 occurrence 局部覆盖会扩张渲染、导出、历史、资源分析和 Agent 协议的语义。本轮更合理的是复用既有 Main 页面与引用机制，先解决定位和影响范围，再做显式变体。固定旧版本用于冻结内容，不能代替“可继续编辑的独立变体”。

**验收条件。** 同一页在 3 个位置出现，修改共享 Main 后所有 live 引用更新，固定版本保持原内容；删除一次出现不删除 Main。若实现独立变体，仅目标 occurrence 改为新身份，其他出现、固定版本和原 Main 不变；新页的资源、动画目标和撤销边界正确。以 80 页、多个 Presentation、重复页和章节引用混合的样本验证定位与编排效率。

### W7：Plugin 的下一步应是实际安装用户的入口与验证

**证据。** [`plugins/huandeng/README.md`](../../plugins/huandeng/README.md) 已有 stdio MCP、15 个工具、`HUANDENG_ENTRY` / `HUANDENG_CLI` 及 Codex/Claude 配置示例；其说明也承认真实客户端安装链尚未验证。默认 launcher 路径面向源码布局。桌面准备脚本 [`prepare-desktop-workspace.mjs`](../../scripts/prepare-desktop-workspace.mjs) 只复制 core 和 desktop，未复制根目录 `plugins/`；桌面帮助菜单目前只有关于信息，编辑器没有可发现的 Agent 连接入口。这不影响当前 CLI/MCP 本身已存在，但会阻止普通安装用户将协议能力转为使用能力。

**建议。** 添加“连接 Agent”说明入口，围绕当前安装和项目生成可复制的配置：识别客户端类型、当前项目路径、实际 CLI 路径、所需运行环境及本地权限范围。先做可检查的配置与诊断，再在具备客户端环境时完成一次真实连接和只读工具调用。已连接状态必须来自实际可观测事实；本地文档服务在线只说明编辑器服务可用。

**取舍。** 本轮不需要内嵌聊天面板，也不需要建立公开网络服务。Windows 路径、空格转义、Node 可用性、未打开项目以及只读工程的行为，均比在界面上增加 Plugin 标志更接近真实可用。配置生成和正式加载客户端是不同完成级别，发布说明应分开标记。

**验收条件。** 使用打包后的应用及含空格的项目路径，可以从入口得到真实可运行、无需源码 checkout 的配置；不猜测用户机器的安装目录。无项目、运行环境缺失或路径无效时给出明确诊断。至少一个目标客户端成功列出工具并读取当前项目，才能将该客户端标为已验证；写入验证使用副本并经过既有单写者事务，而非绕过编辑器直接覆写 `.page`。

## 5. 文档漂移与不应回退的现有能力

`PROJECTS.md` 仍使用旧的英文 UI 名称，并称 `S1` / `S2` 为主要页面标签、四位短码为兼容别名；当前页面显示和 v0.6 交付约定优先使用四位短码。该文档须与最终 UI 和身份约定同步，否则 Agent 和用户会沿不同术语操作同一项目。此项可并入 W2/W6 的实施，不另设一条大优先级。

以下现有能力应作为回归前提保留：草稿冲突时不覆写外部变更；Main 与 Presentation 的共享关系；固定版本的资产快照；缺失引用时明确阻断；文本输入与键盘作用域；资源复用而非强制复制；将本地服务状态和外部 Agent 状态分开。审计并未发现足够理由推翻这些方向。

## 6. 交给总 Audit / Spec 的决策建议

建议负责人优先采纳 W1–W4 的交互修正，并把 W5 的最小可播放动态交付和性能审计共同列为本次里程碑的硬验收项。W6 的定位/导航可随本轮完成，完整变体事务应由模型风险决定；W7 可以先交付可见入口与有效配置，真实客户端验证单列结果。

本报告没有给全部项目笼统打“已完成”结论，也没有把每一项研究建议视为必须立即实现。最终总 Spec 应为选中项写明：用户起点、完成路径、文件/项目影响范围、失败与取消行为、验证样本和剩余边界。完成这些之后，再由负责人批准实现范围。
