# HUANDENG 0.15 性能审计

日期：2026-11-10（Australia/Sydney）。审计对象是已安装的 0.15.0 Windows 包，运行源码 `100659c513161356413eb9ef3707f6e772a64897`；交付源码主线 `07c58c573da60fc841ed7e463272bb244e3ee87d`。本轮新增测量工具与审计记录，性能改造尚未实施。

## 结论

存在可感知的慢响应，尤其是长稿切页、章节浏览中的图片准备和新进程打开项目。没有观察到崩溃、丢稿或持续空闲忙循环，也没有足够证据判定内存泄漏。

优先修复两条路径：**浏览预览按可见范围保留，而不是浏览过就常驻；图片准备区分当前画面与后台预览，并缓存可复用的结果。** 然后优化切页和外部 Agent 修改后的刷新成本。不要通过取消写入版本检查来换取速度。

## 方法与边界

- 两个现有项目分别复制到临时目录：Deck A 为 26 页、268 个对象，Deck B 为 92 页、1,681 个对象。每次启动使用独立配置和文档服务，不操作用户正在编辑的窗口。原项目的入口、页面和元数据逐文件校验，所有运行前后均一致。
- 每个项目先探索一遍，再执行三次正式独立运行。第一遍的交互结束时间包含自动化往返开销，已从延迟汇总中剔除。正式计时在 renderer 内从捕获输入事件开始，到目标 DOM 条件成立后两帧结束；它不是显示器上的精确像素呈现时间，也不代表图片全部解码完成。
- 每项目正式样本包括 21 次切页、12 次进入浏览、两遍全稿滚动及视图往返。最后一次另测四次备注输入/保存/还原，以及图片响应。原文件不被这些操作改写。
- Windows，Ryzen 7 8845H，16 个逻辑处理器、31.3 GiB 可见物理内存。测试时原编辑器及其他应用保持运行，正式运行开始可用内存约 1.8–2.3 GiB。没有清空系统文件缓存，故“新进程启动”不能叫严格磁盘冷启动。未与其他编辑器做同机速度赛跑。
- 统计来自真实安装包；[脱敏汇总](evidence/performance-v015/summary.json)和[可重跑脚本](../scripts/benchmark-workspace-v015.mjs)保留。完整原始记录、项目副本及路径留在用户本机数据目录，不进入 Git。

## 测量结果

| 指标 | 26 页 Deck A | 92 页 Deck B | 解读 |
|---|---:|---:|---|
| 新进程启动至画布就绪，中位数 | 4.46 s | 6.31 s | 各 3 次；范围分别 4.35–4.55、5.83–7.01 s |
| 切页，中位数 / 样本 P95 | 144 / 207 ms | 313 / 531 ms | 各 21 次；大稿最慢 558 ms，已经能感觉到等待 |
| 进入章节浏览，中位数 | 102 ms | 251 ms | 各 12 次；不包含全稿图片准备完成 |
| 备注输入，中位数 | 44 ms | 85 ms | 各 4 次；是粘贴一段备注的响应，不是连续中文输入法测试 |
| 备注输入到落盘，中位数 | 853 ms | 960 ms | 包含现有 700 ms 防抖及最多约 50 ms 文件轮询误差 |
| 保存请求到响应头，中位数 | 106 ms | 218 ms | 各 4 次，全部 HTTP 200；不与输入响应混算 |
| `/current` 读取，中位数 | 12 ms | 57 ms | 各 9 次；含本地 HTTP 和完整响应读取 |
| `/session` 重新扫描读取，中位数 | 39 ms | 169 ms | 各 9 次，明显重于 current |
| 完整 snapshot 响应大小 | 162,221 B | 896,108 B | 即使修改很小，全量回读仍有成本；这不是发给模型的上下文长度 |
| 图片请求到响应头，中位数 / 最大 | 69 / 695 ms | 1,151 / 6,473 ms | 最后一次运行记录到 37 / 195 个响应；包含浏览器排队、服务及转换等待，不含完整解码时间 |

样本量较小，P95 只描述本轮样本尾部，不是线上服务保证。92 页样本完整浏览后额外等待约 2.98 秒，图片未完成计数才归零。观测到的图片响应全部为 HTTP 200，没有将加载错误误称为慢请求。

## 按优先级的发现

### P1：章节浏览保留所有已经看过的页面——已复现

`WorkspaceSlidePreview` 的 IntersectionObserver 首次进入范围后将 `visible` 设为 true 并断开观察，离开屏幕不会卸载。26 页样本从 9 个浏览渲染器增加到 26 个；92 页从 6 个增加到 92 个。后者 DOM 节点从 4,422 增到 12,963，图片节点到 286 个。滚回顶部后仍保持这个数量。

第二遍数量不再增加；离开浏览回到编辑后浏览渲染器归零。这支持“单个浏览视图内的常驻成本”，不支持“无限泄漏”。三次正式大稿浏览合计观测到 36 个超过 50 ms 的主线程任务，最长 120 ms；尚未证明每一个长任务都由常驻预览单独造成。

依据：[workspace-views.tsx](../packages/core/src/app/components/pptd/workspace-views.tsx)；对照左栏的 [thumbnail-rail.tsx](../packages/core/src/app/components/pptd/thumbnail-rail.tsx)，后者会删除离屏项的可见标记。

建议：共享一个观察器或用按行窗口化的网格；只保留可见行与相邻缓冲行的复杂 renderer。卡片位置、键盘焦点和章节标题仍可保留；选中项、重复引用、固定版本必须按 occurrence/version 身份缓存。不能用未经版本绑定的缩略图冒充当前页面。

### P1：大稿图片准备显著落后于界面响应——已复现，具体成本占比待分解

大稿图片响应头等待最长 6.47 秒；浏览切换本身只有约 0.25 秒。因此仅测按钮响应会遗漏真正的“画面迟迟出不来”。

[asset-preview.ts](../packages/core/src/pptd/asset-preview.ts) 已有两条并发槽、队列限制和 128 MiB / 256 项缓存，属于必要的资源保护。但原图与预览走同一个调度器；缓存和 304 判断之前仍读取原图字节并计算内容哈希，派生预览又是会话级目录。当前选中画面的原图可能与后台缩略图竞争。这些是源码证据；本轮未把浏览器排队、磁盘读、哈希、转换、GPU 解码逐项独立计时。

建议：当前画面优先、离屏预览取消或降级；以内容 revision + 尺寸作为派生图缓存键；在有界缓存和可靠失效机制下复用跨会话缩略图；补齐请求队列/读文件/转换/发送分阶段记录。不要直接把并发从 2 放大到几十，也不要以 mtime 代替写前内容校验。

### P2：长稿切页和启动有优化空间——已测量，尚未定位唯一根因

大稿切页中位 313 ms、样本 P95 531 ms；新进程至可用画布约 5.8–7.0 秒。`huandeng.tsx` 承担整个工作区状态，页面选择会让较大的组件树参与更新；导航仍为所有页面建立卡片结构与标题。不能仅凭这个结构就断言 React 是全部耗时来源。

建议：给启动划分服务就绪、首次 snapshot、入口脚本、首屏 renderer、首屏图片阶段；对慢切页采集 CPU/渲染记录，区分对象渲染、缩略图滚动、布局和图片。标题、检索文本、章节分组按页面 revision 与元数据 revision 缓存，避免每次选择或输入都重新计算全稿。

另有可直接看到的放大因素：`SectionBrowser` 为每张卡片的两个移动按钮调用 `workspaceMoveBoundary`，内部再次 `findIndex`；一轮形成 O(n²) 的页序查找。92 页时不能证明它主导延迟，但到数百页不值得保留。应使用已有 index 或一次建立 key→index 表。

### P2：Agent／外部修改仍触发全量刷新——源码确认，影响部分测量

`PptdDocumentClient.ensureEvents()` 收到新事件后调用 `refresh()`，最终走 `/session`；服务执行 `refreshExternal()`，重新读取文档。watcher 本身也会触发刷新，存在重复扫描的可能。完整大稿 snapshot 约 0.90 MB。后端已做内部页面复用、前端也做 `shareSnapshot`，因此不能说“完全没有增量优化”。

`huandeng_context` 向模型返回的是投影摘要，但 MCP 适配器先通过 `client.session()` 获取完整 snapshot 再投影；不应把 0.90 MB 当成模型 token 消耗。这里值得优化的是服务到适配器的内部读取和扫描次数。

建议：首次连接、断线重连、手动刷新继续做完整校验；可靠事件通道下按 changedPages 与 sequence 获取差量，事件缺口回退全量。每个写事务继续做真实字节与 expected revision 校验。增加服务端 context 投影端点，批量执行已审阅的同组操作，避免 Agent 高频重复读全稿。

### P2：多项目常驻与长时使用——风险，尚未完成规模验收

桌面每个打开项目保留自己的 WebContentsView 和文档服务；切换时只是 `setVisible`，没有卸载后台 renderer。这样能保留草稿和快速切换，也增加常驻开销。本轮只对一个隔离项目做性能采样，不能推导 5–10 个项目的内存曲线。

建议后续分别测 1/2/5 个项目、长时间浏览和 Agent 连续写入。若需要后台降载，应保留 writer/草稿并暂停非必要预览，先解决保存与恢复语义，再考虑休眠。

## 没有发现或不能据此判定的事项

- 空闲三秒采样的 renderer 主线程活动很低；不是持续轮询把 CPU 打满的证据。
- JS heap 有垃圾回收波动；未强制 GC，也未做数小时 retained-heap 对照，不能宣称“无泄漏”或“已经泄漏”。进程 working-set 求和还可能重复计入共享页，不能直接当成唯一物理占用。
- 自动保存约一秒不全是卡顿：700 ms 防抖是明确设计。应呈现“正在编辑／待保存／已保存”，而非为了数字好看取消防抖。
- 隔离运行的操作历史端点在写入前返回空数组，故本轮没有覆盖大量既有 journal 的历史加载性能。复制的项目保留页面与元数据，但会话级状态隔离。
- 未覆盖持续拖拽、复杂图表/公式、千页稿、原始 OneDrive I/O 延迟、导出时并发编辑、物理输入法候选窗以及其他编辑器的同题实测。

## 下一版验收建议

以下是建议目标，尚不是已达成指标：

| 改造 | 验收方式 |
|---|---|
| 浏览预览窗口化 | 92/300 页来回三遍，复杂 renderer 数受可见行与缓冲行约束；不能随看过页数增长；章节折叠、键盘、固定版本回归通过 |
| 图片调度与缓存 | 单独测首次和重复浏览；记录当前页图片的 P50/P95 与服务分阶段成本；不存在离屏任务压住当前页的队列 |
| 切页 | 同一硬件和样本先争取中位 ≤150 ms、P95 ≤250 ms；统计同时报告可用内存、图片完成情况及原始样本 |
| 输入与保存 | 输入反馈 P95 ≤100 ms；防抖后提交另计，不能以减少冲突校验换指标 |
| 外部事件差量 | 连续 50 次单页修改，未变页面不重传；断线、乱序、缺口、同长度文件修改仍正确恢复或拒绝冲突 |
| 启动 | 先完成阶段拆分，再分别制定新进程和缓存命中启动预算，避免只优化空白窗口出现时间 |

开源能力取舍见 [开源对照与采用建议](AUDIT-V015-OPEN-SOURCE.md)。
