## 4. 前后端补充审计

### 前端

Undo/Redo 记录 operationId、draft 投影 WeakMap、图表 SVG 32 项/8 MiB LRU、缩略图窗口挂载及主要 Effect 清理均已存在。没有证据支持重新添加全局 memo 或定时强制 GC。导出页面目前一次渲染全部页并解码所有图片；视频必须只挂载当前 occurrence、固定时钟采样，并使用有限在途帧。新导出 UI 需要明确范围和 cue 停留，辅助草稿保持阻断。

### 后端

ExportManager 完成/失败后只关浏览器，现存任务继续持有工作资源。新实现必须区分活跃工作资源与可下载的完成态产物。完成态不能指向后来会被同名导出覆盖的文件；失败和取消不能留下伪成功文件。项目关闭必须停作业、杀掉本作业编码子进程并清理临时文件。

历史优化不能删除磁盘版本，也不能取消同长度/恢复 mtime 的外部变化检测。获取已提交状态与明确扫描磁盘应分开；保存、事件、恢复和 Agent 可见顺序保持一致。SSE 慢消费者和只读过时请求是后续可测风险，尚无证据称已发生持续泄漏。

### 动态交付可行性

比较 [FFmpeg](https://ffmpeg.org/ffmpeg.html)、[image2pipe](https://ffmpeg.org/ffmpeg-formats.html#image2pipe)、[WebCodecs](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API) 与 [Mediabunny](https://github.com/Vanilagy/mediabunny)。本机已有 FFmpeg，实际隔离编码生成 320×180、30 fps、30 帧、1 秒 H.264 MP4，ffprobe 验证通过。这仅证明编码器可用，尚不证明 PPTD 动画导出已完成。

决定复用 FFmpeg，避免新引入编码/封装依赖或实时录屏时钟。应用通过显式配置、随包工具目录或 PATH 发现编码器；不硬编码本机路径。逐帧输出复用现有渲染器和 timeline sampler，PNG 通过管道背压编码。GIF/可自主运动 SVG 不得被错误描述为已同步媒体时间，导出必须冻结或明确阻断并报告；原始资源不改写。

## 7. 最终验收后的负责人判断

最终包与正式安装通过，详细收据见 Validation。验收没有支持“长会话内存已经解决”这一结论：80 页副本 50 轮中，文档服务工作集约212–223MiB波动，renderer 仍增至497.30MiB，GC后约397.83MiB。缓存上限、派生预览、正常关闭和大部分可回收JS对象都不能替代 renderer 残余持有的归因。此项保留为下一轮P0。

相邻同脚本20轮旧/新包对照又确认：文件可见时间中位211.65→255.45ms，操作恢复可用495.05→418.50ms，画面反馈26.30→26.85ms。负责人接受“提交后重复刷新减少，确认阶段变短”，拒绝直接将文件可见延后归因历史缓存、磁盘写入或watcher。下一轮需要记录事务接收/入队/开始、watcher排队、页面安装和收尾的分段时间，先验证180ms watcher 与下一次连续操作的队列相位，再决定实现；不削弱CAS、fsync和恢复保障。

UI最终实图也保留了具体改进项：1040×680时间轴打开时整页虽完整可见，但适配仅约31%；素材双滚动区和常驻技术说明仍占空间。下一轮先调整工作面积和说明密度，再单独验收125%/150%系统DPI。本轮接受发布的依据是实际工作流、数据正确性和交付能力已完成既定门槛，而非忽略这些剩余问题。
